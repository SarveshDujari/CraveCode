# Phase 2 status — 22 October 2026

CraveCode has a signed-in **local Swiggy demo** and a public **Render preview**. The local workflow searches up to four meal themes, reads a second menu page when Swiggy supplies one, deduplicates menu items, filters diet/stock/exclusions, checks restaurant ratings and review counts, and ranks up to 15 choices. Restaurant area, distance, and delivery time appear when Swiggy provides them. A good rating is presented as customer feedback, not a food-safety guarantee. Search-source timeouts keep slow Swiggy calls from holding the entire response indefinitely.

Local menu results can show deliberately broad calorie/protein ranges for recognizable dish names. These are handwritten, illustrative dish-profile ranges with serving assumptions, **not verified restaurant nutrition**. Unsupported or complex combinations show no estimate. The method and limitations are in `NUTRITION_METHOD.md`. No Gemma-generated numeric nutrition claims appear. The exact-match verdict remains unverified until a restaurant-specific source exists.

The first search uses deterministic dish planning. In the signed-in local demo, a separate “Explore more dishes with Gemma” action asks a small local Gemma model to choose up to three diet-filtered dish themes, then checks whether those bounded Swiggy queries yield new menu items. If the model returns nothing usable, a safe rule-based fallback chooses themes and the UI identifies that fallback. This action reports the themes tried and actual new item count; it uses one demo search only when new themes exist. An offline, name-match fixture found 22 proxy hits with the extra themes versus 15 without; live Swiggy yield is **not yet verified** and may differ. Run `npm run gemma:evaluate` while the local Ollama endpoint is available to repeat the fixture.

Render remains a public web preview while Swiggy Builders production access is pending. It makes **one SerpApi Google request per uncached search** and labels all results as web leads, with no claim that an item is available, deliverable, within budget, or nutrition-verified. The server caps each browser session at **five search attempts**, persisted in Atlas for the 24-hour session window. A separate global SerpApi guard permits **five request attempts per UTC day and 100 per UTC month** across the Render service; it fails closed if Atlas is unavailable. A cached identical query uses no new SerpApi credit. Browser cookies can be cleared, so the global guard is the hard credit ceiling.

Atlas is connected on Render and stores search jobs, candidates, session counters, and SerpApi counters. Render was verified on commit `165c7fc` with `/api/health` reporting `searchRevision: 6`; `/api/system` reported `mongo: connected` and `demoSearchRemaining: 5` for a fresh session. The revised multi-theme Gemma action still requires the owner to check it in their signed-in local browser. Cart verification remains deferred; no order is placed by this workflow.

The production build and 28 automated checks pass in this workspace. That verifies parsing, ranking, nutrition labeling, pagination, filtering, and local budget behavior, but cannot establish live menu coverage or real restaurant macro accuracy.
